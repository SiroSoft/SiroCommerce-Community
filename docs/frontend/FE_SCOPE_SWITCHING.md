# Frontend CommerceScope Switching

Status: `FE DESIGN BASELINE`

CommerceScope is the four-part context used to isolate commerce reads and
writes:

```text
store_id + channel_id + locale + currency
```

The server validates this context. The browser must make it explicit and must
never silently fall back to a default scope.

## Scope Contract

| Header | Value rules |
|---|---|
| `X-Store-Id` | 1-64 characters matching `[A-Za-z0-9_-]` |
| `X-Channel-Id` | 1-64 characters matching `[A-Za-z0-9_-]` |
| `X-Locale` | `en`, `vi`, `ja`, `de`, or `zh` |
| `X-Currency` | `VND`, `USD`, `EUR`, `JPY`, or `CNY` |

Equivalent query parameters `store_id`, `channel_id`, `locale`, and `currency`
are accepted for clients that cannot set headers. The FE should use headers.
Sending both forms with different values is an ambiguous request and must not
be generated by the client.

## Scope Store

Keep one canonical scope store outside individual components:

```text
ScopeStore
  activeScope: { storeId, channelId, locale, currency } | null
  availableScopes: server-provided and role-filtered
  generation: monotonically increasing integer
  status: uninitialized | loading | ready | switching | invalid
```

Rules:

- Do not render scoped data until `activeScope` is complete and validated.
- Do not select a scope from a URL, resource ID, cached response, or user-entered arbitrary string.
- Display the complete scope in the switcher, not only the store name.
- A switch is an explicit user action and increments `generation` before new requests start.
- The request layer reads the scope at dispatch time, never when a component first mounts.
- Include all four values in query-cache keys and request de-duplication keys.
- A response is accepted only if its request scope and generation equal the current scope.
- Abort or ignore in-flight requests from the previous scope.
- Do not optimistically merge old-scope rows into the new scope.

## Switch Transaction

1. Disable the switcher and show the pending target scope.
2. Increment `generation` and cancel/ignore old-scope requests.
3. Clear or namespace scoped query caches before the first target request.
4. Persist only the non-sensitive scope selection, preferably per user and environment.
5. Reload the minimum bootstrap data for the target scope.
6. Invalidate dependent lists, detail views, dashboards, forms, and mutation drafts.
7. Re-enable the switcher after bootstrap success; announce the new scope accessibly.
8. On failure, keep the previous scope only if no target-scope data was rendered; otherwise move to `invalid` and require a fresh selection.

The switch must not log the user out. It must not change the customer identity,
cart token, access token, or refresh token. A cart token is scoped to its cart,
not a substitute for CommerceScope.

## Cache Isolation

At minimum, every scoped query key contains:

```text
environment + operationId + store_id + channel_id + locale + currency + parameters
```

Mutation invalidation is also scope-qualified. Examples:

- `post_api_admin_pages_id_publish` invalidates only the target page/revision and published-content keys for the active scope.
- `put_api_admin_products_id` invalidates only product/catalog keys for the active scope.
- `get_api_admin_orders` and `get_api_admin_orders_id` never share entries across scopes.
- Analytics and reports include their requested date/filter dimensions plus scope.

Never use only a slug, numeric ID, operation path, or component name as a
cache key. Do not persist scoped response bodies in a global browser store.

## Scope Errors And UI

| Server condition | Stable FE behavior |
|---|---|
| Missing scope | Block the request, show scope selection, do not retry with defaults |
| Header/query mismatch | Client bug; emit a redacted diagnostic and fix request construction |
| Unsupported scope value | Show unavailable target and reload available scopes |
| `403` | Show scope access denied without revealing another tenant |
| `404` | Show resource absent in the active scope; do not probe other scopes |
| `409` | Refetch in the same scope and show the conflict |
| `401` | Follow session recovery; retain scope only as non-sensitive UI state |

Use the normalized envelope `{success:false,message,meta}` and
`meta.error_code`/`meta.errors`. Do not parse the human-readable message to
identify scope failures. If the backend introduces a dedicated scope error
code, add it to the normalized error enum before shipping the UI.

## Role And Scope Interaction

Scope availability is the intersection of the selected scope and the
authenticated role/capability. The switcher must not list scopes the identity
cannot access. Backend denial remains authoritative for stale membership,
revoked access, and object-level checks.

When a user changes role, logs out, or receives `401`/`403` for the active
scope:

- stop scoped polling;
- clear scoped response data and drafts;
- retain no resource identifiers in the URL beyond the safe navigation target;
- require bootstrap of a valid scope after authentication recovery.

## Acceptance Tests

- Missing one of the four headers prevents a scoped request and never causes a default-scope request.
- Header and query values that differ are rejected by client tests before transport.
- Switching from `S1/C1/en/USD` to `S2/C2/vi/VND` leaves no visible S1 rows after target bootstrap.
- An old slow response cannot overwrite target-scope data after a switch.
- The same slug, product ID, order ID, and page ID have distinct cache entries by complete scope.
- A scoped mutation sends the same scope used by the form load and invalidates only that namespace.
- Browser reload restores a permitted non-sensitive scope selection but never restores access or token material.
- A `403` or scope validation error does not trigger scope probing or fallback.
- Two tabs switching scope do not corrupt each other’s local cache or active session; each request carries its tab’s selected scope.
- The historical 38-operation `x-scope` slice is contract-tested; current source has 62 markers and the full set must be regenerated before release evidence.

## Known Contract Gap

The current OpenAPI `x-scope` marker covers 63 operations (the 38-operation list
above is historical) and explicitly
documents the four headers for CMS/headless operations. Some route families
also enforce scope in backend services without carrying the same marker in the
generated document. FE transport should send the active scope to all admin
commerce requests, but release tooling must add a contract assertion that
every scope-enforced route advertises `x-scope` before treating this as closed.
