# CG-005 through CG-008

## CG-005 Reporting parity

The three v2 report operations use the `reports` capability and the same
`store_id`/`channel_id` query scope. Their date window is `from`/`to`; failures
also uses page/per-page pagination. The OpenAPI generator is the source of
truth for these markers and `REPORTING_OPERATIONS` keeps the admin boundary
aligned without duplicating backend authorization.

## CG-006 Browser session and CSRF

Access tokens remain memory-only. Refresh calls are POST-only, origin-checked,
rate-limited, and never place tokens in URLs. Cookie-authenticated writes must
use `credentials: "include"` and provide `X-CSRF-Token`; the shared transport
rejects such writes before network dispatch when the token is absent. The
current backend refresh contract remains body-based until an HttpOnly refresh
cookie contract is published.

## CG-007 Error envelopes

Frontend errors consume only `meta.error_code` and `meta.errors`. The shared
normalizer preserves `meta` and rejects malformed field-error values instead of
accepting legacy top-level `errors`.

## CG-008 Shared transport

`RequestCoordinator` owns versioned `Accept`, CommerceScope headers, cart and
idempotency headers, generated correlation IDs, CSRF transport, coordinated
refresh/replay, and response metadata. Generated SDK output is not hand-edited.
